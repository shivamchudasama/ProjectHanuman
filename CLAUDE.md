## Repository nature

**Project Hanuman**: **Zephyr / nRF Connect SDK firmware** for a BLE device that receives an Intel HEX upload over BLE and can store it as a file on the DK's external flash, can be provisioned with a device certificate, and can pair with another provisioned device by certificate-based OOB pairing. It exposes GAP, Device Information, the SETU service and the Pairing service, and runs both `_LIB/SETU` roles. A MikroE MCP2518FD Click on `spi21` adds a CAN / CAN FD bus (`_ASW/_CAN`), on which the device itself diagnoses and flashes ECUs with UDS (`_LIB/UdsClient`, the tester side, since Zephyr only has ISO-TP) over Zephyr's ISO-TP, triggered over BLE (`_ASW/_UDS`); raw CAN frames are not exposed over BLE. Six users share SETU through an appType router, behind a gate: a provisioned device serves only its one **trusted host** (host authentication), and advertises only while DK Button 3 has opened its host window.

Names: the project is *Project Hanuman* (GitHub repo `ProjectHanuman`; the device advertises as `ProjectHanuman`). The transfer protocol is **SETU** (Sliding-window, Error-checked Transfer Utility; formerly BulkXfer, same UUIDs and wire format), meant as the standard across BLE projects. Code, file names, the GATT service and the PC tools say SETU (`SETU_*.h`, `gi_SETUS_*`/`gi_SETUC_*`/`gi_SETURouter_*`, `_SETU_SVC`, `setu_client.py`); the plain word "bulk" stays. The captures in `_LOG/` predate the rename and keep the old names.

The six users:

- **Hex upload** (`0x10`–`0x1F`). A PC client (the GUI in `_TOOLS/BleHostGUI`, or `setu_client.py hex`) sends each contiguous segment as one transfer, `[u32 LE address][data]` with appType `0x10`. The segment is buffered in RAM and logged on the UART. Framed by BEGIN `0x12` (file name) and COMMIT `0x13` (`hex --store`, the GUI's "Store as"), the upload is also written, a record `[addr][len][data]` per segment, to `/FLASH_DISK:/FW/UPLOAD.TMP` and renamed at COMMIT; FILE `0x14` answers with status, size and CRC-32. Contract: `_DOC/HexUpload/PROTOCOL.md`.
- **File commands** (`0x40`–`0x4F`, `CONFIG_FS_CMD`): the FileSystemPoC's UART test harness over BLE (CMD/REPLY/ENTRY short messages), driven by the GUI's Files page and `setu_client.py fs`. Contract: `_DOC/FileSysManager/PROTOCOL.md`.
- **Device provisioning** (phase 1 of certificate-based authentication and pairing, `_DOC/CBAP`), appTypes `0x20`–`0x2F`. The device keeps a persistent P-256 key and CSR. The PC acts as the CA: it fetches the CSR (the device sends it with its SETU Client to a SETU service the PC hosts) and returns the CA and device certificates. The device holds the verified CA in RAM; once the device certificate verifies against it, it stores both in PSA ITS, deletes the CSR and logs both as PEM. Stored certificates are re-verified at boot. Provisioning is one-time: a wipe (DEPROVISION `0x27`, or DK Button 0 held 5 s) destroys key, CSR and certificates (and pairing bonds) and makes a fresh key and CSR. Contract: `_DOC/Provisioning/PROTOCOL.md`; design and limitations: `_DOC/Provisioning/README.md`.
- **Device pairing** (phase 2, AN1396 §4.2), appTypes `0x30`–`0x3F` between two devices. A host (GUI Pairing page, or `setu_client.py pair`) writes START (role, peer address) to each device's Pairing service and follows its STATUS. The peripheral advertises directed to the central, the central connects; each device moves both SETU roles to that peer link (router filter: only `0x30`–`0x3F`), exchanges and verifies device certificates, sends its fresh LE SC OOB data signed with its device key over `r‖c‖sender‖receiver`, verifies the peer's, and pairs with OOB at level 4, bonded; the central writes SECURED (LESC-only), the peripheral lights LED0 (`DK_LED1`). Each saves a bond record (role, peer) in settings; whenever the bonded link is down (reset, link loss) the peripheral advertises directed to the central and the central scans, connects and encrypts with the stored keys, and at level 4 both blink LED0 while the link is up. A device holds one host link and one peer link. Contract: `_DOC/Pairing/PROTOCOL.md`; design, security and limitations: `_DOC/Pairing/README.md`.
- **UDS** (`0x50`–`0x5F`, `CONFIG_UDS_CMD`). A host (the GUI's ECU page, or `setu_client.py uds`/`flash`, with a JSON profile per ECU) sets the target (CAN configuration, IDs, timing), sends raw UDS requests (DIAG_REQ, the response in 236-byte DIAG_RSP parts), unlocks (UNLOCK, on-device seed→key), and starts a flash job (FLASH: a stored upload's name + 34 bytes of sequence parameters; RESULT at once, then STATUS until DONE/FAILED/ABORTED; ABORT, STATUS_REQ). The device runs the job: it reads the file twice (check + CRC-32, then send), locks the bus, and runs the parameterised ISO 14229 sequence (10 03, 85 02, 28, 10 02, 27, 2E fingerprint, 31 erase once or per record, 34/36/37 per record, 31 check with the CRC, 11). The bench ECU is `_TOOLS/EcuSim`. Contract: `_DOC/UDS/PROTOCOL.md`; design, sequence, profiles, security and limitations: `_DOC/UDS/README.md`.
- **Host authentication** (`0x60`–`0x6F`, `_ASW/_HOST_AUTH`). The PC holds a host credential: a P-256 key and a host certificate from the provisioning CA (EKU clientAuth; `issue_host()`, the GUI's Host access page, `setu_client.py hostcert`).
  - Handshake: HELLO `[1][Nh][Qh][host cert]` → CHALLENGE `[1][Nd][Qd][SigD][device cert]`, sent with the device's Client to the PC's service → FINISH `[SigH]` → RESULT. Both signatures are over T = SHA-256 of the label, nonces, ephemeral points and both certificate hashes, with role labels "dev"/"host".
  - Passkey: HKDF-SHA256 of the ECDH secret, mod 10⁶. The PC pairs with LE SC passkey entry (Windows `ProvidePin`, `core/winrt_pairing.py`); the host link's SMP callbacks (`bt_conn_auth_cb_overlay()`, `app_passkey`: DisplayOnly) allow only that pairing.
  - The bonded host at level 4 is the one trusted host (record `hauth/host`). The router's gate admits only it, except for `0x60`–`0x6F` and GET_STATUS `0x20`, plus `0x20`–`0x2F` on an unprovisioned device; Pairing CONTROL gives others ATT `0x08`.
  - DK Button 3 (SW3): a press opens the host window (120 s undirected advertising, LED1 blinks); held 3 s it forgets the host first. A trusted host's link loss opens a 60 s grace window; an untrusted host's gives back the rest of the window it closed.

  Contract: `_DOC/HostAuth/PROTOCOL.md`; design, security and limitations: `_DOC/HostAuth/README.md`.

- SDK: **NCS v3.4.1** (Zephyr 4.4.2), toolchain `C:\ncs\toolchains\4f5b6ad6dd`.
- Board: **`nrf54l15dk/nrf54l15/cpuapp`**.
- Built from VS Code's nRF Connect extension (sysbuild) into `build/`. The build configurations are versioned as presets in the root `CMakePresets.json` (`build`: SPI, `build_sqspi`: sQSPI), which the extension offers when adding a build configuration; change a configuration there (or with its "Save Configuration as Preset"), not only in a build folder. After the linker's FLASH/RAM summary, the `mem_report` target (root `CMakeLists.txt`) prints the same per module of `_ASW` and `_LIB` and writes `zephyr/mem_report.txt`. After a layout or config change, do a **pristine** build — a stale `build/` keeps cached paths.
- Command-line build: use PowerShell with the toolchain's `environment.json` variables (PATH, PYTHONPATH, `ZEPHYR_TOOLCHAIN_VARIANT`, `ZEPHYR_SDK_INSTALL_DIR`) plus `ZEPHYR_BASE=C:\ncs\v3.4.1\zephyr`, and run `west build` **from the repo directory**. Git Bash breaks the toolchain's Python (`ctypes` error), and running from `C:\ncs` fails because the source is on another drive. Use a separate `-d build_<name>` so VS Code's `build/` is left alone.
- Tests: host tests in `_TEST/` (C with CMake + CTest + Unity against a Zephyr shim, Python with pytest), run locally with `_TEST/run_tests.ps1` (report in `build_test/report/`; `-Static` adds the static analysis gate, `-Fuzz` the libFuzzer targets, which need clang/LLVM) and in CI by `.github/workflows/ci.yml`, which also runs both of those and builds the firmware in Nordic's toolchain container. "Done" means the tests pass and the board above builds cleanly. Local host gcc is Strawberry's 4.4, so test code stays gnu99 and avoids newer GCC features. It has no sanitizers and misses warnings that CI's GCC 13 (64-bit Linux, `-Werror`, ASan/UBSan) reports, such as `%d` for a `ssize_t` or a one-byte overread, so a change is done only once CI passes too.

Source files follow the BATL coding guidelines in `_DOC/BATL Coding Guidelines/` (file banner, section headers, Hungarian-style prefixes such as `gv_`, `su8ar_`, `scar_`). `Sample_Format.c`/`.h` there are the templates for new files. `_LIB` sources (and `AppLog.h`) use the same layout but carry an MIT licence header (`SPDX-License-Identifier: MIT`) instead of the BATL copyright. The Python tools in `_TOOLS` are not covered by BATL; they follow ordinary PEP 8 style.

## Layout

- `README.md` — the repo overview: status, SETU / hex upload / file system / provisioning / pairing / host authentication / CAN / UDS in brief, layout table, building, PC usage, testing, documentation links, licence. Kept current per *Routine*.
- `CMakePresets.json` — the build configurations (board, `_DI/prj.conf`, the board overlay, `FLASH_IF`); never list the `flash_<if>` files in it.
- `CMakeLists.txt` — sets `KCONFIG_ROOT` to `_DI/Kconfig` and defaults `CONF_FILE` to `_DI/prj.conf` and `DTC_OVERLAY_FILE` to `_DI/boards/<board>.overlay`; reads `FLASH_IF` (`spi` default, or `sqspi`; under sysbuild a `-D` reaches the image only through `SYSBUILD_CACHE`, which it parses itself) and defaults `EXTRA_CONF_FILE`/`EXTRA_DTC_OVERLAY_FILE` to `_DI/conf/flash_<if>.conf` and `_DI/boards/<board>_flash_<if>.overlay` (Zephyr merges extra files from every scope), and stops with a message if a build configuration passes those flash files itself (added twice, ninja fails; as `DTC_OVERLAY_FILE` they replace the board overlay); then pulls in `_ASW` and `_LIB`, and adds the `mem_report` target (runs `_TOOLS/MemReport/mem_report.py` on the map after each relink). Never set `APPLICATION_CONFIG_DIR`: Zephyr resolves a relative `CONF_FILE` against it, so the extension's `_DI/prj.conf` would become `_DI/_DI/prj.conf`.
- `_ASW/` — application software. `main.c` plus one folder per module:
  - `_BLE/` — stack init (`bt_enable()`, then `settings_load()` for bonds, then `gv_HostAuth_OnBtReady()` and `gv_Pair_OnBtReady()`), advertising, connection callbacks, and per-link PHY/DLE/MTU negotiation (so SETU's `b_autoTuneLink` is off), then, on links where the device is peripheral, a 7.5–15 ms connection-interval request (Zephyr sends it 5 s after connecting; `CONFIG_BT_GAP_AUTO_UPDATE_CONN_PARAMS` stays `n`). The interval is what sets upload throughput; Windows ignores the peripheral's request and settles on ~45 ms, so the GUI requests 15 ms itself. Every connection is offered to `gb_Pair_ClaimConn()` first (the peer link: a run's, or the bonded peer's); the first other one is the host link (`gstpt_BLE_GetHostConn()` returns a new reference; `gv_HostAuth_OnHostConnected()` gets it before SETU), a second host is refused. Forwards disconnects to SETU, `_PAIR` and `_HOST_AUTH`, and security changes to `gv_Pair_OnSecurityChanged()` and `gv_HostAuth_OnSecurityChanged()`. Undirected advertising runs only while `gb_HostAuth_WindowOpen()` and no host is connected, and only while `_PAIR` does not hold the advertiser; it carries the Pairing service UUID once provisioned, the SETU UUID before (the name is in the scan response), plus manufacturer data `FF FF 01 <flags>` from `gv_HostAuth_GetAdvData()` (provisioned, host bonded), set at each start, so a PC removes its stale keys for a device without a host bond. Otherwise, while `gb_Pair_AwaitsBondedPeer()`, it advertises directed to `gb_Pair_GetBondedPeer()`. `gv_BLE_RefreshAdv()` re-evaluates it.
  - `_SETU_SVC/` — the SETU GATT service (DATA, CTRL + CCC, CAPS) built on `GATT_CB`. `gstpt_SETUSvc_Init()` returns the CTRL attribute. `SETURouter.c` owns `gi_SETUS_Init()` and `gi_SETUC_Init()`: modules register an appType range (with optional `fpt_onTxDone`/`fpt_onCliReady`) with `gi_SETURouter_Register()`, then `gi_SETURouter_Start()` starts both roles and dispatches each callback by appType. Unregistered types are rejected. `gv_SETURouter_SetFilter()`/`ClearFilter()` admit only one range (the peer link). `gi_SETURouter_SetGate(admit, refused)` (before Start) installs `_HOST_AUTH`'s gate, consulted for every new transfer and short message while no filter applies. `gi_SETURouter_ClientAttach(conn, ownerAppType)` attaches the shared Client for a module, detaching it from another link first; `-EALREADY` means ready on that link.
  - `_DATA_STORE/` — hex upload (`0x10`–`0x1F`): receive callbacks, the 64 KiB segment buffer (`DS_BUF_SIZE`) and a low-priority dump thread (3 KiB, an event queue: segment, BEGIN, COMMIT) that logs each verified segment: with `CONFIG_DS_HEX_DUMP=n` (currently set in `prj.conf`), one `SEG addr= len= crc=` line; with `CONFIG_DS_HEX_DUMP=y` (debugging; several seconds per 64 KiB), every byte as `0xADDR: xx …` lines paced by `log_buffered_cnt()` so the deferred log never drops lines. While an upload is open (BEGIN … COMMIT) it writes the segment's record with `gi_FSMGR_Call()` before STORED (status SINK_ERROR once a write failed). Sends RESULT/STORED/FILE short messages. `gi_DataStore_Init()` registers its range; `gb_DataStore_UploadOpen()` tells `_FS_CMD` the open file is taken.
  - `_FS_CMD/` — file commands (`0x40`–`0x4F`): a CMD from the engine thread becomes one `gi_FSMGR_Submit()`; the result callback sends ENTRYs and the REPLY from the manager's thread. One command at a time; BUSY while one runs, an upload is open or a UDS flash job runs (`gb_UdsJob_FlashRunning()`, with `CONFIG_UDS`). `gi_FsCmd_Init()` registers the range (only with `CONFIG_FS_CMD`).
  - `_CSR/` — from the reference `Sample Code/_ASW`, ported to NCS 3.4. `gt_InitCryptoStorage()` (settings under `CONFIG_SECURE_STORAGE_ITS_STORE_IMPLEMENTATION_SETTINGS`, `psa_crypto_init()`, then a check that the HUK exists, which NCS writes in crypto init; once; an `#error` if secure storage takes its key from the HUK library without `CONFIG_HW_UNIQUE_KEY_WRITE_ON_CRYPTO_INIT`); `gv_GenerateOrLoadCSR()` generates (first boot or after a wipe) or reuses the persistent PSA key `CSR_DEVICE_SIGNING_KEY_ID` (`0x0001`) and builds or restores the CSR (`gst_CSRData`, kept in PSA ITS until provisioned); `gt_RemoveStoredCSR()`, `gt_DestroyDeviceCredentials()` (key + CSR), `gt_ProbeDeviceKey()`. `DER.c` is the minimal CSR encoder (Zlib notice kept). CN is an RFC 4122 UUIDv5 of the hardware ID; the other subject fields come from Kconfig `CSR_SUBJ_*`.
  - `_DEVICE_CERT/` — certificate buffers (`gst_CACertData`, `gst_deviceCertData`) and their ITS storage (`DeviceCert.c`: one entry each, UID `"DEVCERT"`‖3 for the CA and ‖1 for the device; `gt_StoreCACert/DeviceCert()`, `gt_LoadStoredCerts()` returns the pair or nothing, `gt_RemoveStoredCerts()`, `gv_ClearCertData()`). `DeviceCert_Verify.c` holds the mbedTLS X.509 + PSA checks: `ge_VerifyCACertificate()`, `ge_VerifyOwnDeviceCertificate()` (with the CSR subject), `ge_VerifyStoredDeviceCertificate()` (boot, without it), `ge_VerifyRemoteDeviceCertificate()` for phase 2, and `ge_VerifyHostCertificate()` (host authentication: EKU clientAuth required; device certificates must not carry it). They follow the BG22/BG24 reference in `Sample Code Device Cert Verification`, with its defects fixed. Links `mbedtls_external`.
  - `_PROV/` — the provisioning protocol (`0x20`–`0x2F`): router callbacks (check, copy to a staging buffer, post), a low-priority thread (10 KiB stack) for verification, storage and the wipe, the CSR sent with the router's shared Client to the host link, STATUS/RESULT and PEM logging. It owns no cryptography. `gi_Prov_Init()` restores a stored pair (re-verified; wiped if invalid) or calls `gv_GenerateOrLoadCSR()`. A wipe is refused while `gb_Pair_IsRunning()`, and afterwards calls `gv_Pair_ForgetBonds()` and `gv_HostAuth_Forget()`; becoming provisioned or wiped calls `gv_BLE_RefreshAdv()`. `ProvButton.c` (NCS DK library) turns a held Button 0 into `gv_Prov_RequestWipe()`; it is a separate file with its own test (`prov_button`, DK-library shim).
  - `_PAIR/` — certificate-based pairing (`0x30`–`0x3F`). `Pair.c`: the state machine on its own thread (10 KiB): CONTROL/STATUS, directed advertising or scan + connect, the peer link (`gb_Pair_ClaimConn()`), SETU moved to it and back, certificate and OOB exchange, SMP callbacks (`pairing_accept` only on the verified peer link, deferred `oob_data_request` answer), SECURED, timeouts (`CONFIG_PAIR_*`), UNPAIR, the bond record (settings `pair/peer`, static handler) and bond restore at boot, the bonded reconnection (central scans/connects/encrypts, peripheral awaits; level 4 within 10 s, retry after 1 s), and the LED (one work item: steady after pairing, blinking on a reconnected link). `PairOob.c`: the signed OOB frame (PSA ECDSA, raw r‖s). `PairSvc.c`: the Pairing GATT service (`B1C10000-…`), BT-only. CONTROL is the trusted host's only (`gb_HostAuth_IsTrustedConn()`, ATT `0x08` otherwise); the bond restore skips the host's bond (`gb_HostAuth_IsHostAddr()`); `gb_Pair_GetBondedPeer()` for directed advertising.
  - `_HOST_AUTH/` — host authentication (`0x60`–`0x6F`). `HostAuth.c`, on its own thread (6 KiB, priority 10):
    - router callbacks, HELLO/CHALLENGE/FINISH/RESULT/STATUS/REFUSED; one buffer holds HELLO, then CHALLENGE, reserved until the transfer ends;
    - the gate (`gb_HostAuth_Admits()`, installed with `gi_SETURouter_SetGate()`);
    - the host link's SMP callbacks through `bt_conn_auth_cb_overlay()` (`pairing_accept` after FINISH only, `app_passkey` = the derived passkey), and a `bt_conn_auth_info_cb`;
    - trust = the bonded host's address at level 4 (a Security Request when it reconnects); the record `hauth/host` (static settings handler), one host bond;
    - the window, the grace window, the 30 s timeout, LED1 (`DK_LED2`, one work item);
    - hooks `gv_HostAuth_OnHostConnected/Disconnected/SecurityChanged()` and `OnBtReady()`; `gv_HostAuth_Forget()` for the wipe;
    - `gv_HostAuth_GetAdvData()`, the advertised state; advertising is refreshed when the host bond goes.

    `HostAuthCrypto.c`: the ephemeral ECDH key, the transcript, role signatures with the device key, the HKDF passkey (PSA only). `HostAuthButton.c`: Button 3 (`DK_BTN2_MSK`) through `dk_button_handler_add()`, a press opens the window and a hold (`CONFIG_HOST_AUTH_FORGET_HOLD_MS`) forgets the host.
  - `_CAN/` — `CanIf.c`, the one owner of the CAN controller (`DT_CHOSEN(zephyr,canbus)`, the MCP2518FD): boot configuration from Kconfig, `gi_CanIf_Configure()` (classic/FD, listen-only, bitrates; stop, apply, start, roll back on failure), `gi_CanIf_Send()` (blocking, validates the frame), `gi_CanIf_AddRxFilter()` (driver callbacks on its cooperative interrupt thread only queue `{slot, generation, frame}`; the module's thread (2 KiB, priority 6) calls the user, and frames for a removed filter are dropped), state listeners and bus-off count (the queue keeps 2 entries for state changes), a bus lock for a session (`gi_CanIf_Lock(owner)`: others' Configure gets `-EBUSY`), a rate-limited traffic log (two catch-all driver filters, `gv_CanIf_SetMonitor()`), bench-only self-test and test frames (the MCP2518FD's `CAN_MODE_LOOPBACK` is external loopback: they go out on the bus), `gstpt_CanIf_GetDevice()` for ISO-TP later. Built only with `CONFIG_CANIF`.
  - `_UDS/` — UDS diagnostics and flashing (`0x50`–`0x5F`), built with `CONFIG_UDS`. `UdsJob.c`: one thread (3 KiB, priority 7) and a 2-deep queue, one job at a time (`gu8_UdsJob_SetTarget/Diag/Unlock/Flash/Abort`, results through callbacks on that thread; they return `UdsResult_E`, the wire status codes); between jobs it calls `gi32_UdsClient_KeepAlive()` (no timer: ISO-TP runs on the system work queue). TARGET applies `gi_CanIf_Configure()` then `gi_UdsClient_SetTarget()` (the ISO-TP transport is created on the first target, on `gstpt_CanIf_GetDevice()`; padding must match `CONFIG_ISOTP_ENABLE_TX_PADDING`). A flash job scans the file (records, CRC-32) through `gi_FSMGR_Submit()` reads, locks the bus (`gi_CanIf_Lock()`, owner `&sst_client`), turns the traffic log off, listens for bus-off, runs the sequence, restores everything and calls `gv_UdsClient_EndSession()` after a failure; `gb_UdsJob_FlashRunning()` from acceptance to the end. `UdsKey.c`: BENCH_XOR (algo 1) and `gi_UdsKey_Oem()` for `0x80`–`0xFF`, compiled from a git-ignored `_UDS/oem/` (the module's CMake file then defines `UDS_KEY_OEM`). `UdsCmd.c`: the router callbacks (decode, hand to UdsJob or refuse at once; pad byte only 0/0xCC, no extended addressing) and RESULT/DIAG_RSP/STATUS from the job thread. The router has 6 route slots (`SETU_ROUTER_MAX_ROUTES`), all used.
  - `_WDT/` — `Wdt.c`, the application watchdog (`CONFIG_APP_WDT`): logs and clears the hwinfo reset cause, starts the task watchdog with the hardware watchdog (alias `watchdog0`, `wdt31`) as fallback, and feeds one channel (`CONFIG_APP_WDT_TIMEOUT_MS`, no callback: an expiry reboots) from a 1 KiB supervisor thread at `K_LOWEST_APPLICATION_THREAD_PRIO` every `CONFIG_APP_WDT_FEED_MS`, so a hang or a starved CPU resets the device; `gu32_Wdt_ResetCause()`. Further channels per thread can be added with `task_wdt_add()` (5 channels). `gi_DataStore_Init()`, `gi_FsCmd_Init()`, `gi_Prov_Init()`, `gi_ProvButton_Init()`, `gi_Pair_Init()`, `gi_HostAuth_Init()`, `gi_HostAuthButton_Init()`, `gi_CanIf_Init()` (with `CONFIG_CANIF`), `gi_UdsJob_Init()` and `gi_UdsCmd_Init()` (with `CONFIG_UDS`), `gi_SETURouter_Start()`, `gv_BLEInitStartAdv()`.
  - `_GAP/` — Device Information GATT service. GAP itself is Zephyr's built-in service (`CONFIG_BT_GAP_SVC`); device name and appearance are set by `CONFIG_BT_DEVICE_NAME`/`CONFIG_BT_DEVICE_APPEARANCE` in `prj.conf`. Never define a second GAP service — the host allows exactly one, and `bt_enable()` fails with `-EINVAL`.
  - `_BLE_GENERIX/` — Bluetooth SIG UUID and appearance tables (headers only).
  - `_APP_LOG/` — `APP_LOG` logging module; `AppLog.h` has `APP_LOG_ERR/WRN/INF/DBG`, which prefix `__func__`.
  - `_GENERIX/` — generic helpers.
- `_DI/` — build configuration. `prj.conf` lives here, not at the root. Windowed ACKs, Go-Back-N, CRC-32 per object (needs `CONFIG_CRC`). Each role binds one link; `gi_SETUS_Rebind()` and `gi_SETUC_Detach()` move it between live links (refused mid-transfer). `SETU.h` is the umbrella header; tunables in `SETU_Config.h`. The transport interface `UdsTp_T` is in `UdsClient_Types.h`; `UdsTp_Isotp.c` implements it on `isotp_bind/send/recv` (BS 0, STmin 0; an oversized message is drained, -EMSGSIZE). Tunables in `UdsClient_Config.h`. Docs in `_DOC/UdsClient/`, tests in `_TEST/unit/UdsClient/`.

**Adding a module or library:** create `_ASW/_NAME/` (or `_LIB/<LIB>/`) with a `CMakeLists.txt` copied from a sibling (it globs `*.c` into `app` and adds its folder to the include path), then `add_subdirectory(_NAME)` in `_ASW/CMakeLists.txt` (or `_LIB/CMakeLists.txt`). Every module folder is on the include path, so headers are included by bare name. A module is not done until it has the tests below, and a library or tool until it also has the docs.

## Library, tool and module requirements

Every new unit ships with tests, added in the same change and kept current with it: each `_LIB` library, `_TOOLS` tool and `_ASW` module, and every new file in an existing one. Only code that does nothing but call the Zephyr BT stack (`_BLE`, `_GAP`, `SETUSvc.c`, `main.c`) is left to the firmware build and `hil-tests`. A library or tool also ships with its docs; an `_ASW` module needs none of its own, but the protocol documents it touches (`_DOC/HexUpload`, `_DOC/Provisioning`, `_DOC/Pairing`, `_DOC/HostAuth`, `_DOC/FileSysManager/PROTOCOL.md`, `_DOC/UDS`) are kept current.

- **Docs** (libraries and tools) in `_DOC/<Name>/` (for a `_TOOLS` tool, beside it, as `_TOOLS/BleHostGUI/README.md`):
  - `README.md` — purpose, overall structure (each file and its role), design rationale, how it fits with the other units, integration steps. Model: `_DOC/SETU/README.md`.
  - `API_REFERENCE.md` — the exact contract of its public headers: types, functions, return/error values, threading, known limitations, so it can be used and modified without reading the source. Models: `_DOC/SETU/API_REFERENCE.md`, `_DOC/GATT_CB/API_REFERENCE.md`.
  - `PROTOCOL.md` — when it defines anything exchanged with a peer: GATT table, message formats, sequences, rejection rules. Model: `_DOC/HexUpload/PROTOCOL.md`.
  - Other documents as the unit needs them (state machines, timing, memory budget).
- **Tests** (every unit), written against the API reference or protocol document and run both locally by `_TEST/run_tests.ps1` and on GitHub by `.github/workflows/ci.yml`:
  - C: Unity tests in `_TEST/unit/<Name>/`, registered with `add_unit_test()`; public headers added to `CHECKED_HEADERS` in `_TEST/CMakeLists.txt`. Cover the normal path, every documented error return, and boundaries.
  - Python: pytest in `_TEST/python/test_<name>.py`, GUI pages included.
  - Code that calls Zephyr/NCS APIs, PSA or a DK library is still tested: extend the shim, stub PSA with `shim/psa_stub`, record the calls. Code whose correctness is the cryptography itself (X.509, signatures) runs on the real Mbed TLS (`mbedx509`). File system code runs on `shim/fs_sim.c`. Only behaviour that needs the radio, CRACEN or flash goes in `hil-tests`.
  - A defect found while writing a test is reported, and documented as a known-bug test until fixed.
  - Wire format changes go into `vectors/wire.json` first.
  - A test that needs a new tool, dependency or job is added to `run_tests.ps1` and `ci.yml` together, so local and GitHub runs stay the same.
